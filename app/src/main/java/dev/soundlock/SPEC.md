# dev.soundlock 包（保护逻辑）

整个保护行为都在这一个包里：什么时候该静音、音量键怎么处理、音量怎么写、浮层怎么显示、外部读到什么状态。跨模块的拓扑与不变量见 `soundlock-architecture`。

## 接缝

四层，依赖单向向内，`GuardService` 是唯一把策略结论变成系统动作的地方：

- **纯策略**（`LockPolicy`、`VolumeKeyGate`、`MuteRefresh`、`VolumeScale`）：只用 Kotlin 标准库，直接单测。任何新规则尽量落在这里，而不是散进服务。
- **适配**（`MediaVolumeControl`、`GuardCapsule`）：唯一碰 `AudioManager` 写音量、唯一碰 `WindowManager` 画浮层的地方。
- **编排**（`GuardService`）：事件源汇总、状态推进、定时器、通知。
- **外壳**（`GuardState`、`MainActivity`、`LockTileService`、`LockReceiver`）：只读快照、只调服务的公开方法，不自己碰音频。

## 上锁与授权（`LockPolicy`）

- `shouldMute` 与 `shouldConfirm` 同式：`armed && !unlocked && route != EXTERNAL`。也就是说"需要静音"和"该弹确认"是同一条件，不存在只静音不提示的中间态。
- 空闲截止时间只在「已启用 && 已解锁 && 未在播放」时存在，等于 `idleSince + idleTimeoutMs`（默认 15 分钟，设置页可在 5 / 15 / 30 / 60 分钟间改）；播放一开始就清空，播放停止时重新起算。改动时长当场重新计算——值本身是派生输入的具名属性，不需要额外状态。反复的空闲检查不会把计时往后推。
- 撤销只有一条路：`lock()`。`unlock()` 只在 `armed && route == SPEAKER` 时成功，其余一律失败。
- 输出路径一变化就 `lock()`，即使只是经过 `UNKNOWN`：授权不能跨设备存活。
- 只有「先读到正数、之后回到零」才撤销授权。刚确认的解锁可能还没被 AudioService 应用，读到的零不代表用户拒绝；但确认后一直是零的授权仍会按时到期。
- 时间一律用 `elapsedRealtime`，从不用日历时间。

## 音量键（`VolumeKeyGate`）

- 只处理音量加；未配对的抬起事件不消费，避免孤立事件吃掉下一次按下。
- 按住期间的重复与抬起继续消费，但只有第一次按下触发确认提示，避免长按连续弹窗。
- 通话、闹钟、铃声等打断音频时整段放行（exempt）；已解锁、外接设备、暂停保护时也放行。
- 决策只有 `consume` / `confirm` / `mute` 三个布尔，不查音频、不渲染、不做 Binder 调用。

## 静音重试（`MuteRefresh`）

- 未处于需静音状态时永远返回 `false`：授权期间不会有任何音量写入。
- 100ms 内不重复写——声锁自己写的设置也会触发观察者回调，否则会变成写循环。
- 读到正数必写；兼容通道下读数只是估计值，即使为 0 也每 500ms 重写一次。`force` 由音量键和状态切换传入，用于立刻重新归零。

## 音量读写（`MediaVolumeControl` + `VolumeScale`）

- 默认走标准媒体流。**兼容通道**的启用条件是三者同时成立：厂商属于 OPPO / OnePlus / realme / OPlus；系统里没有已启用独立音量的无障碍服务（否则会改写读屏用户的音量）；无障碍流有可调范围。此时每次写入都同时写媒体流与无障碍流。
- 兼容通道下 `read()` 返回的是「媒体直读」与「无障碍档位折算」的较大者，`estimated` 与 `unreliableZero` 标出来：最低档折算成 0 只代表可能静音，上层必须继续重试。
- 解锁固定写 1 格媒体音量，折算到无障碍档位时向上取整，保证"授权的最低档"不会又掉回静音。
- 注释里写的「绝不改动独立读屏音量通道」是硬约束，不是可选优化。

## 编排（`GuardService`）

- 事件源：音量键、`Settings.System` 观察者、播放配置回调、音频设备回调、`AudioManager` 模式监听、`ACTION_AUDIO_BECOMING_NOISY`、息屏/亮屏/解锁广播、精确闹钟、以及兜底轮询。
- `inspect()` 是唯一的状态推进点，顺序固定：读输出路径 → 读播放与打断音频 → 刷新音量模式 → 采样音量 → 走时钟 → 需要则静音 → 协调浮层 → 排定时器 → 发布快照。任何异常都走 fail-closed 分支（置 `UNKNOWN`、上锁、尽力归零、给出可见原因）。
- 路由判定：输出里有内置扬声器或听筒 → `SPEAKER`；全部落在识别过的外接类型 → `EXTERNAL`；其余（包括空列表）→ `UNKNOWN`。新增外接类型只加白名单，默认仍是保护。
- 打断音频（闹钟、铃声、通话及其提示）期间既不静音也不弹提示，音量键放行——这一条同时决定浮层可用性（`canInteract` 还要屏幕已解锁）与音量键是否 exempt。
- 拔耳机/断开路由时先用 `ACTION_AUDIO_BECOMING_NOISY` 立即上锁并归零，不等设备查询追上，然后再补一次检查。
- 常驻通知只在保护启用时存在：低优先级、无声音无振动、锁屏隐藏内容，带「确认解锁」与「立即上锁」两个动作。
- `dump()` 是排障入口，输出 armed/unlocked、路由、按键消费数与回调耗时、最后一次解锁结果、音量模式与浮层状态。新增状态时同步加进这里。
- 卸载服务（`onUnbind` / `onDestroy`）时先上锁并尽力归零，再拆掉所有监听、闹钟、浮层与通知。

## 浮层（`GuardCapsule`）

- 两种形态：确认胶囊（标题 + 「恢复最低一格音量」+ 保持静音 / 确认解锁）和短消息（锁定、解锁反馈）。
- `TYPE_ACCESSIBILITY_OVERLAY` + 不抢焦点 + 非触摸模态：不需要悬浮窗权限，也不挡系统音量面板。确认胶囊 10 秒自动隐藏，反馈消息 1.2 秒。
- 浮层创建失败只记录诊断，绝不因此放行音频：授权只走 `confirmUnlock()` 的返回值。
- 轮询可以关掉失效的提示，但轮询永远不会主动打开浮层——只有音量键或用户动作能唤起它。

## 外壳（`GuardState` / `MainActivity` / 磁贴 / 广播）

- `GuardSnapshot` 是唯一状态载体；`armed` 单独持久化在 `SharedPreferences("guard")`，默认 `true`，所以装完就默认保护。
- 服务未连接时，界面只能改 `armed` 这个持久化开关，别的一律显示「尚未开启」并引导去系统设置。
- 首页主按钮随状态切换（开启保护 / 开启服务 / 立即上锁 / 解锁外放 / 重新检查），已解锁时显示 `mm:ss` 倒计时。App 内的解锁还要再走一次确认对话框，失败原因由服务给出（屏幕未解锁 / 保护已暂停 / 输出设备变了 / 系统拒绝）。
- 设置页有四个系统侧入口（服务、通知、精确定时、后台运行）和一项自己的设置：自动上锁时长（5 / 15 / 30 / 60 分钟，存 `SharedPreferences("guard")` 的 `idleMinutes`，未连接服务时也能改，连上后采用）；声锁不代改系统策略。
- 使用说明页的「当前状态」直接读同一份快照，估计音量显示为「约 N」。
- 磁贴：未连接或暂停为 `INACTIVE`；已解锁时点一下立即上锁，其他情况打开 App 让用户在那里操作。
- 所有跨组件的调用都通过 `GuardState.service` 这个当前服务引用；服务不在时所有入口都要能安全降级，不能崩。
